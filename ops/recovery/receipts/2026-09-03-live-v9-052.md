## What this replay caught, and the mint did not

The ACL asset came back reading `contract_id = …/v9-acl` next to
`schema_version = 8`. The mint substituted the identity in the `.json` form
(`"schema_version": 8`) and in the base `.sql` assets, and missed the ACL `.sql`
pair, which carries it as `'schema_version', 8` in `jsonb_build_object` syntax —
a shape no JSON-shaped replace can reach.

Worse, and worth writing down: the unit test that guards ACL identity was written
FROM the mint script rather than from the convention, so it rebuilt v9-acl with
the same incomplete substitution and went green on the gap. A test derived from
the implementation cannot see the implementation's blind spot. The live replay
could, because it reads what the asset actually says.

Both `.sql` ACL assets were corrected and the test now checks the SQL form too.
Re-replayed after the fix: `contract_id v9-acl`, `schema_version 9`, `1/1`.

## What this receipt does NOT claim

- **The `-pgrestore` twins are still unreplayed against a real restore.** v9's twin
  was measured on a `pg_dump`/`pg_restore` of a database built by the alembic
  chain, which proves canonicalisation, not the round-trip of a production dump.
  That waits for the next P1 drill (ticket `58711012`). No score is invented here.
- **A live replay cannot exercise `sequence_shape` the way a restore does**, for
  the reason the runbook already states.
