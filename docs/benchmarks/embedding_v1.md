# Embedding Benchmark v1 — Qodo vs Qwen3-4B vs jina-v3

**Status**: protocol approved (2026-04-12), Phase 0–B complete, Phase C onward pending execution.
**Owner**: brain-v42 retrieval quality + reliability track
**Brain refs**: decisions `27826716` (criteria), `0edf54cf` (scope narrowing), learning `410eb227` (incident).

## 1. Goal

Pick the embedding model that maximises **retrieval quality for Claude in session** (the
primary user of brain-v42) while satisfying a **hard reliability constraint** added after
the 2026-04-12 VRAM-drift incident: zero silent drift, ≥ 50 % VRAM headroom on the target
GPU, healthcheck reproduces the critical inference path.

This is **not** a "fastest model wins" benchmark. Quality first, reliability hard floor,
latency only as a tie-breaker.

## 2. Candidates (locked)

| ID | Model | Format | Backend | Native dim | Bench dim | VRAM (warmup) | Why |
|---|---|---|---|---:|---:|---:|---|
| `qodo` | Qodo-Embed-1-1.5B | safetensors fp16 | sentence-transformers | 1536 | 1536 | ~5.1 GB | Production baseline. Mean pooling, code-tuned. |
| `qwen3-4b` | Qwen3-Embedding-4B-GGUF Q4_K_M | GGUF Q4_K_M | llama.cpp `--embedding` | 2560 | **1024** (Matryoshka) | ~2.5 GB | Highest model capacity tested. Last-token pooling, instruction-aware. |
| `jina-v3` | jinaai/jina-embeddings-v3 | safetensors fp16 | transformers + sentence-transformers | 1024 | 1024 | ~1.5 GB | Best feature set: native late chunking, MRL, Task LoRA, multilingual. |

**Explicitly out of scope** (decision `0edf54cf`): Qwen3-0.6B, BGE-M3, EmbeddingGemma, OpenAI text-embedding-3-*, ColBERT, HyDE, SPLADE, binary quantization.

## 3. Hardware target

- **All bench candidates** run on **dev-pc (192.168.1.11)**, RTX 5070 Ti 16 GiB, via docker
  context `dev-pc`. Three services side-by-side, ports 8023/8024/8025 (TBD), no GPU contention.
- **Production Qodo** on PC Serveur stays untouched. The bench's `qodo` measurement uses a
  fresh container on dev-pc for fair comparison (same hardware, same uptime, same warmup).
- Prod brain-v42 keeps serving traffic during the bench. Zero downtime expected.

## 4. Gold dataset (auto-supervised, leave-one-out)

`search_log` does NOT store query strings (only metrics). `access_log` is empty
(known dead background task, see skill `debug-metrics-sidecar-issues`). We have no real
captured queries. Solution: synthesize from the corpus itself.

### 4.1 Stratified sample

Sample N = 300 entities, weighted to match corpus distribution:

| Type | Corpus | Sample (proportional) | Sample (rounded) |
|---|---:|---:|---:|
| learnings | 1678 | 198.7 | **200** |
| features | 302 | 35.8 | 36 |
| indexed_plan_chunks | 243 | 28.8 | 29 |
| decisions | 220 | 26.1 | 26 |
| snippets | 37 | 4.4 | 5 |
| indexed_plans | 34 | 4.0 | 4 |
| runbooks | 16 | 1.9 | 2 |
| adrs | 3 | 0.4 | **3** (all) |
| **Total** | **2533** | **300** | **305** |

Random sampling (`ORDER BY RANDOM() LIMIT k`) per type, seed = `2026-04-12`.

### 4.2 Query generation per entity

For each sampled entity, Claude generates **3 paraphrased queries** representing different
levels of abstraction:

1. **Literal-paraphrase**: rewords the entity title/intention close to the original wording
2. **Abstract-question**: a "how do I…" / "why does…" question that should land on this entity
3. **Keyword-bag**: 3–6 raw keywords as a search-bar-style query

For each generated query, we also store the **gold entity ID** (the entity it was
generated from) and the **type**. Total queries = 305 × 3 ≈ **915**.

### 4.3 Storage

`bench/embedding_v1/gold_v1.jsonl` — one JSON object per query line:
```json
{
  "query_id": "lit-0001",
  "query": "how to prevent CUDA out of memory on GPU embedding service",
  "variant": "abstract-question",
  "gold_id": "410eb227-845e-411e-b13b-fa28594caa04",
  "gold_type": "learning",
  "gold_excerpt": "first 200 chars of the source for sanity check"
}
```

Generated **once**, committed (or .gitignored if too large), reproducible via seed.

### 4.4 Limitations (acknowledge upfront)

- This is a synthetic benchmark; it does NOT measure adversarial real-world queries
- Bias risk: queries are generated by Claude, models that "think like Claude" may benefit
  unfairly. Mitigation: phrase the generation prompt to vary tone deliberately
- Single-shot retrieval only — does not measure reranker pipeline or hybrid FTS+vector fusion
  (those are downstream of the embedding choice and orthogonal to this benchmark)

## 5. Metrics

For each candidate × each query variant, compute:

### 5.1 Retrieval quality
- **recall@1, recall@5, recall@10**: 1.0 if `gold_id ∈ top-K`, else 0.0
- **MRR**: mean reciprocal rank of `gold_id` (0 if not in top-50)
- **nDCG@10**: standard formula, gain = 1 if id matches gold, 0 otherwise

Aggregate **per type** (learnings vs decisions vs snippets…) AND **per variant** (literal vs abstract vs keyword) AND **overall**.

### 5.2 Operational
- **Embed latency** p50 / p95 / p99 over the full bench run, single-text and batch-of-10
- **VRAM peak** post-warmup, post-100-inferences, post-1000-inferences (drift signal)
- **Reliability flag** ✓/✗: false if any inference returns non-200 OR VRAM saturates >95 % at any point during the run

### 5.3 Quality criteria for "winner"
A candidate is **acceptable** iff:
- `reliability_flag == ✓`
- `vram_peak < 0.90 × gpu_total` (≥ 10 % free always)

Among acceptable candidates, **winner** is the one with highest **MRR overall**, ties broken by recall@5. Latency is informational only.

### Phase 0 — Hardening Qodo (independent of the bench)

Patch repo-root `docker-compose.yml`, service `embedding`:
```yaml
environment:
  - PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
healthcheck:
  test:
    - "CMD-SHELL"
    - >
      curl -sf -X POST http://localhost:8003/embed
      -H 'Content-Type: application/json'
      -d '{"texts":["healthcheck"]}'
      | head -c 10 | grep -q '\['
  interval: 60s
  timeout: 10s
  retries: 3
  start_period: 30s
```
Rationale: PyTorch itself recommends `expandable_segments:True` (in the OOM message). Real
healthcheck would have caught the 2026-04-12 incident 8 days earlier. Independent of which
embedding model wins the bench — Qodo stays in prod for the duration of the bench at minimum.

### Phase C — Stand up bench services on dev-pc

Compose stack `bench/embedding_v1/docker-compose.yml` running on context `dev-pc`:
```yaml
services:
  bench-qodo:        # baseline, fresh container, same image as prod
    image: brain_v42-embedding   # or rebuild from services/embedding/Dockerfile
    ports: ["8023:8003"]
    runtime: nvidia
    deploy: { resources: { reservations: { devices: [{ driver: nvidia, count: 1, capabilities: [gpu] }] } } }
  bench-qwen3-4b:    # llama.cpp server
    image: ghcr.io/ggerganov/llama.cpp:server-cuda
    command: >
      -m /models/qwen3-embedding-4b-q4_k_m.gguf
      --embedding --pooling last
      -ub 8192 --port 8024 --host 0.0.0.0
    volumes: [./models:/models:ro]
    ports: ["8024:8024"]
    runtime: nvidia
  bench-jina-v3:     # FastAPI sidecar around sentence-transformers
    build: ./jina-v3-server
    ports: ["8025:8000"]
    runtime: nvidia
```
Models pre-downloaded into `bench/embedding_v1/models/`:
- `Qwen3-Embedding-4B-GGUF` Q4_K_M (~2.5 GB) from `Qwen/Qwen3-Embedding-4B-GGUF`
- `jinaai/jina-embeddings-v3` via HF transformers cache (~1.1 GB)
- Qodo image already built locally; ensure same hash as prod

Sanity contract for all 3 services:
- `POST /embed {"texts":[...]}` → `[[float...]]`
- `GET /healthz` → `200` (must touch model, not just process)

### Phase D — Gold dataset generation
Script `bench/embedding_v1/gen_gold.py`:
1. Connect to brain-v42 prod Postgres (read-only)
2. Per-type stratified sample (seeded)
3. For each entity, send `(title, body_excerpt)` to Claude (via brain MCP or directly via Anthropic API) with the 3-variant prompt
4. Validate: gold_excerpt non-empty, query non-empty, no PII leakage
5. Write `gold_v1.jsonl`
6. Print histogram of query lengths and types

### Phase E — Measurement
Script `bench/embedding_v1/run_bench.py`:
1. Load `gold_v1.jsonl`
2. For each candidate:
   - Restart its container to start from clean VRAM (`docker --context dev-pc restart bench-<name>`)
   - Embed the **305 source entities** (one batch per type, sub-batched if needed) → in-memory matrix `(305, dim)`
   - Embed the **915 queries** one-by-one (measure p50/p95/p99 single-text latency) AND in batches of 10 (batch latency)
   - Compute cosine similarity matrix `(915, 305)`
   - For each query, top-50 by similarity, compare to `gold_id`, record rank
   - Sample VRAM via `nvidia-smi` query through `docker --context dev-pc exec` at warmup / 100-inferences / 1000-inferences
3. Aggregate metrics per candidate × per type × per variant
4. Write `bench/embedding_v1/results_v1.json`

Estimated runtime: ~20 min per candidate (1220 embeds + matrix math), ~1h total.

### Phase F — Report & decide
Script `bench/embedding_v1/report.py`:
1. Read `results_v1.json`
2. Render `bench/embedding_v1/report_v1.md`:
   - Headline table (candidate × MRR / recall@10 / VRAM peak / reliability)
   - Per-type breakdown table
   - Per-variant breakdown table
   - Latency table
   - Verdict block
3. If verdict is unambiguous, propose:
   - `brain_propose_adr` for the chosen embedding architecture
   - `brain_log_decision` recording the result
   - Migration plan (separate document, NOT executed in this benchmark)
4. If inconclusive:
   - `brain_learn` documenting why
   - Next-round candidates / variations

## 9. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Synthetic queries favor models that "think like Claude" | Use varied prompts; report per-variant breakdown so the bias is visible |
| 305 entities is too small a sample | Stratification + 3 variants = 915 queries; 95 % CI on recall@10 stays tight enough at this size |
| Qwen3-4B Q4_K_M quantization degrades quality vs full precision | Acknowledge: we test Q4_K_M as the actually-deployable variant. If it loses, retest with Q5_K_M or bf16 in v1.1 |
| llama.cpp `--pooling last` differs from sentence-transformers default — embeddings non-comparable | Each model bench is self-contained (queries embedded by SAME model that embedded the corpus); we never cross-compare raw vectors, only ranking |
| dev-pc image / library version drift causing flakiness | Pin all images to digests; run end-to-end smoke test before measurement |
| brain-v42 prod search degrades during bench (Qodo stress) | Bench runs on a separate Qodo instance on dev-pc, prod is untouched |
